# 阶段一双人协作计划

## 1. 目的与边界

本计划服务于阶段一 `0.1 g（100 mg）` 加粉目标。软件先形成可稳定执行、可验收、可追溯和可回放的闭环；L0 参数表为生产基线，ILC 仅以影子模式生成建议，不自动改变实机动作。

协作按职责而不是按文件随意拆分：

- **设备集成负责人（A）**拥有实物设备和在线执行链路。
- **数据与算法负责人（B）**拥有数据合同、离线回放、模型和参数优化链路。
- 任何在线动作都必须经过 A 的安全状态机；B 的算法只能输出受限的候选动作计划，不能直接下发串口命令。

## 2. 协作总链路

```text
B: 配方 / CandidatePlan
          |
          v
A: 在线安全状态机 -> 设备驱动 -> 实物设备
          |                             |
          +--------- RunRecord <---------+
                       |
                       v
B: 数据校验 -> 回放仿真 -> L0/尾量/ILC 影子分析
                       |
                       +---- 下一版 CandidatePlan
```

## 3. 双方职责

| 项目 | A：设备集成与在线执行 | B：数据与算法 |
| --- | --- | --- |
| 设备驱动 | 维护 AT8811C、LA10 和后续给粉/门控/互锁驱动 | 定义驱动提供给算法的观测字段与动作语义 |
| 真实执行 | 实现在线状态机、急停、互锁、超时、重试和安全退出 | 不直接占用串口或执行实机动作 |
| 标定实验 | 执行空载、带容器、标准砝码、动作量-质量和余粉实验 | 设计采样要求、分析数据，提出下一轮实验参数 |
| 数据记录 | 以统一 RunRecord 格式记录完整事实 | 维护数据格式、校验完整性、建立可回放数据集 |
| L0 参数 | 按标定实验产生候选数据并确认设备能力边界 | 建立查表/插值规则，形成待审批的 L0 版本 |
| ILC | 只接收经批准的参数版本，不接受算法直接控制 | 离线/影子计算、冻结/回退建议、效果报告 |
| 验收 | 确认设备行为、保护链路和日志是否真实 | 确认误差、漂移、重复性和学习样本是否合格 |

## 4. 共同冻结的数据合同

### 4.1 CandidatePlan：B 提交给 A 的候选动作计划

CandidatePlan 只描述工艺意图和安全边界，不含 Modbus 帧、COM 口或设备私有参数。

```json
{
  "schema_version": "1.0",
  "plan_id": "plan-20260721-001",
  "recipe_id": "powder_a_100mg",
  "target_mg": 100,
  "parameter_version": "l0-001",
  "stages": {
    "coarse": {"action": 1200, "stop_margin_mg": 30},
    "slow": {"action": 180, "stop_margin_mg": 8},
    "fine": {"pulse_action": 20, "max_pulses": 6}
  },
  "limits": {
    "hard_overweight_mg": 105,
    "max_duration_s": 120,
    "max_retry_count": 1
  }
}
```

**A 需要确认**：每个 `action` 在实际设备中的含义、单位、最大值和停止确认方式。  
**B 需要确认**：所有数值来自已标定的参数版本，且不突破配方安全边界。  
**输出**：可执行或被拒绝原因明确的 CandidatePlan。

### 4.2 RunRecord：A 返回给 B 的完整过程事实

每个任务使用唯一 `run_id`，以下字段必须关联到同一个任务：

| 记录类别 | 必填内容 |
| --- | --- |
| `task` | `run_id`、操作者、时间、配方、粉体批次、头型、目标质量、最终判定 |
| `parameter_snapshot` | CandidatePlan、L0/L1 版本、设备配置、算法版本、配置哈希 |
| `weight_trace` | UTC 时间、单调时钟、重量 mg、原始计数、稳定/零区状态、CRC 与通信结果 |
| `command_trace` | 动作名称、计划值、实际下发值、开始/结束时间、命令确认、执行器状态 |
| `state_trace` | 状态机进入/退出时间、切换原因、等待时间、重试次数 |
| `alarm_trace` | 报警码、严重级别、设备状态、处置、人工干预 |
| `result` | 最终质量、误差、耗时、是否合格、失败/复核原因 |

**A 需要确认**：记录来自真实设备返回值，不能用推测值补齐。  
**B 需要确认**：字段齐全、单位一致、时间顺序正确，才能进入 L0/ILC 数据集。  
**输出**：可回放、可审计的 RunRecord 文件。

## 5. 阶段拆分与交付物

| 阶段 | A：设备集成与执行 | B：数据与算法 | 共同确认 | 阶段输出/退出条件 |
| --- | --- | --- | --- | --- |
| 0. 接口冻结 | 列出设备、COM 口、地址、动作范围、互锁与急停行为 | 定义 CandidatePlan、RunRecord、单位、报警码与版本规则 | 动作单位、质量单位统一为 mg、时钟语义、可接受空字段 | `schemas/v1`、设备清单、接口评审记录 |

## 6. 在线与离线边界

### A 的在线安全边界

- 即使 CandidatePlan 合法，A 的执行器仍必须检查互锁、行程、最大动作量、超时、通信和硬性超量。
- 天平通信失败、稳定质量不可信、执行器故障或人工急停时，立即停止给粉并写入 RunRecord。
- 在线状态机不修改历史 L0/L1 参数；只读取已审批的参数快照。

### B 的离线算法边界

- 仅使用通过数据质量检查的 RunRecord 训练/分析。
- 漂移超限、无稳定质量、人工干预、堵料、超量或通信异常的任务不得进入 ILC 样本。
- 算法输出必须被限幅并带有参数版本、适用粉体/头型和置信说明。
- B 通过模拟器和回放测试所有 CandidatePlan；实机执行由 A 决定。

## 7. 文件与分支所有权

```text
src/powder_sampling_control/
  device_adapters/          # A 维护
  task_state_machine/       # A 主维护，B 评审状态与事件语义
  dispensing_algorithm/     # B 维护
  weighing/                 # B 主维护，A 提供真实设备语义
  data/                     # B 维护
schemas/                    # B 起草，A 必须评审
config/devices/             # A 维护
config/recipes/             # 共同评审
scripts/                    # 按设备/分析脚本分别归属
logs/                       # A 产生，B 只读分析
tests/                      # 每个模块所有者维护；接口测试共同维护
```

- A 使用 `feature/device-*`、`feature/executor-*` 分支。
- B 使用 `feature/algorithm-*`、`feature/data-*` 分支。
- 任何 `schemas/`、`config/recipes/`、安全阈值或公共接口变更都必须由双方评审。
- 禁止两人同时占用同一个 COM 口；实机测试窗口由 A 预约，B 使用已归档 RunRecord 做离线工作。

## 8. 每轮联调的固定节奏

1. **B 提交实验计划**：CandidatePlan、目标、要验证的假设、所需日志字段。
2. **A 预检设备**：通讯、互锁、天平基线、设备配置和安全边界。
3. **A 执行并归档**：不修改 B 已提交的计划；所有偏离和人工操作写入 RunRecord。
4. **B 进行数据校验与回放**：先判断数据可否使用，再输出误差、漂移、尾量和下一版参数建议。
5. **共同评审**：决定接受、拒绝、扩大实验或回退参数；形成下一轮唯一的参数版本。

- 完成天平预热、空载/带载漂移、清零和标准砝码测试；当前漂移异常的任务标记为不可学习。

- 起草 `schemas/v1`，实现 CandidatePlan 和 RunRecord 的格式校验。
- 建立日志回放与质量评估：稳定窗口、短时方差、漂移、缺失字段、通信异常。
- 用模拟 Feeder 和历史天平日志实现四段状态机回放。

### 双方立即确定

- 天平质量门限：允许短时波动、允许基线漂移和拒绝执行/拒绝学习的阈值。
